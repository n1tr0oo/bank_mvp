## 2. Краткое описание AI-версии MVP

«Bank Credit MVP — AI» — функциональный аналог системы из Задания 1, но реализованный на минимальном стеке Flask + SQLite + Jinja2 в одном файле `app.py` (~245 строк). Поддержаны те же бизнес-функции: регистрация и логин, подача и просмотр заявок, решение менеджера, админ-страница со списком пользователей, поиск.

**Стек:**

| Компонент | Реализация в AI-версии |
|---|---|
| Web framework | Flask 2.0.1 |
| БД | SQLite (один файл `bank.db`) |
| Шаблоны | Jinja2 3.0.1 |
| Сессии | Flask session (cookie с `itsdangerous`) |
| Хеширование пароля | `hashlib.sha256` (без соли) |
| Запуск | `python app.py` (development server, `debug=True`) |
| Контейнеризация | отсутствует |

**Соответствие минимальным требованиям ПР6.**

| Требование | Реализация в AI-версии |
|---|---|
| UI | 7 страниц на Jinja2 (login, register, apps, new_app, app_detail, admin, base) |
| ≥5 эндпоинтов | 8 маршрутов: `/`, `/register`, `/login`, `/logout`, `/apps`, `/apps/new`, `/apps/<id>`, `/apps/<id>/decide`, `/admin/users`, `/search` |
| ≥3 сущности БД, ≥200 строк | 2 таблицы (users, applications). Сидируется 214 пользователей, 220 заявок |
| ≥2 роли | `client`, `manager`, `admin` |
| Полный сценарий | Регистрация → подача заявки → решение менеджера → просмотр |
| Проверка ввода | Минимальная (HTML-атрибуты `required`, `type="email"`, `type="number"`) |
| Хеш паролей | SHA-256 без соли |
| Разграничение прав | Декоратор `@login_required` + `if user["role"] != "manager"` локально + `{% if %}` в шаблонах |
| Журналирование | Отсутствует (только Flask-стандартный access log) |
| Секреты вне кода | Отсутствует — `secret_key = "supersecret123"` в коде |
| Docker | Отсутствует |

**Дефицит против Задания 1:** только 2 сущности (нет `audit_logs` и `revoked_tokens`); нет логирования; нет Docker; нет `.env`; нет rate limiting.

## 3. Архитектура AI-версии

```
   Browser  ─►  Flask development server (debug=True, host=0.0.0.0)
                         │
                         │  app.py
                         │   ├ session cookie (без HttpOnly/SameSite)
                         │   ├ маршруты: register, login, apps, decide, admin, search
                         │   ├ ветвление по session['role']
                         │   └ render_template (Jinja2 — autoescape по умолчанию)
                         ▼
                  SQLite файл (bank.db)
                  ├ users (id, email, password sha256, full_name, role)
                  └ applications (id, client_id, amount, purpose, term_months, status, ...)
```

В отличие от Задания 1 нет: middleware (security headers, body size, rate limiting), dependency-системы (разделение `get_db`/`get_current_user`/`require_role`), сервисов (audit/security/csv_export), отдельных Pydantic-схем валидации, миграций. Всё «свалено» в один файл.

## 4. Роли пользователей и разграничение доступа в AI-версии

| Роль | Регистрация заявки | Просмотр своих | Просмотр всех | Решение | Список пользователей | Поиск |
|------|:-:|:-:|:-:|:-:|:-:|:-:|
| **client** | ✅ | ✅ (фильтрация на сервере) | ❌ (но **обходится через IDOR**) | ❌ | ❌ (но шаблон показывает страницу) | ✅ (с SQLi) |
| **manager** | ❌ | — | ✅ | ✅ (без проверки текущего статуса) | ❌ (только `if` в шаблоне) | ✅ |
| **admin** | ❌ | — | ✅ | ❌ | ✅ | ✅ |

Нюансы реализации:
- `current_user["role"]` берётся из БД при каждом запросе — корректно. Но `session["role"]` дублируется при логине и используется в шаблонах напрямую — несинхронизировано после смены роли.
- Регистрация принимает `role` из формы → любой клиент при регистрации может выбрать `admin`.
- На `/apps/<id>` нет проверки `client_id == user.id` — IDOR.
- На `/admin/users` — только `@login_required`, проверка роли в шаблоне; данные всё равно загружаются из БД.

## 7. Таблица выявленных уязвимостей AI-версии и предлагаемых мер

| № | Категория OWASP | Место | Описание | Возможные последствия | Критичность | Предлагаемое исправление |
|---|---|---|---|---|---|---|
| 1 | A01 Broken Access Control / CWE-639 IDOR | `app.py` `app_detail` | `SELECT * FROM applications WHERE id=?` без проверки `client_id == current_user.id` | Клиент видит чужие заявки по перебору ID | Высокая | Добавить проверку владельца либо вернуть 404 для чужих |
| 2 | A01 Broken Access Control | `app.py` `admin_users` | Серверная проверка только `@login_required`, роль проверяется в шаблоне | Любой залогиненный получает 200 с данными пользователей в HTML | Средняя | Перенести проверку на сервер: `if user.role != 'admin': abort(403)` |
| 3 | A01 Broken Access Control / CWE-915 Mass Assignment | `app.py` `register` | `role = request.form.get("role", "client")` | Самостоятельная регистрация с ролью `admin` | Средняя | Игнорировать `role` из формы; зашить `role='client'` |
| 4 | A02 Cryptographic Failures | `app.py` `hash_password` | `hashlib.sha256` без соли и итераций | Подбор пароля по словарю/радужным таблицам тривиален | Высокая | Заменить на `bcrypt` (через passlib) или `argon2-cffi` |
| 5 | A02 Cryptographic Failures | `app.py` line 24 | `app.secret_key = "supersecret123"` хардкод | Подделка session cookie злоумышленником | Средняя | Вынести в `.env` (минимум 32 байта энтропии); требовать переменную окружения |
| 6 | A03 Injection / CWE-89 SQLi | `app.py` `search` | `sql = f"SELECT * FROM applications WHERE purpose LIKE '%{q}%'"` | Полный обход фильтра, чтение/изменение БД | Высокая | Использовать плейсхолдеры: `cur.execute("... LIKE ?", (f'%{q}%',))` |
| 7 | A04 Insecure Design / CWE-841 | `app.py` `decide` | UPDATE без проверки текущего статуса | Менеджер может пересмотреть уже принятое решение | Средняя | Добавить `WHERE status='pending'` либо проверку до UPDATE → 409 |
| 8 | A04 Insecure Design | `app.py` `new_app` | Принимаются любые `amount`/`term_months` без диапазона | DoS через гигантские числа, бизнес-логические нарушения | Средняя | Валидация: `amount in (0, 10_000_000]`, `term_months in [1, 360]` |
| 9 | A05 Security Misconfiguration / CWE-94 | `app.py` line 244 | `app.run(debug=True)` | Werkzeug debugger даёт RCE через console pin | Высокая | Только production WSGI (gunicorn/uvicorn), `debug=False`, не вызывать `app.run` в production |
| 10 | A05 Security Misconfiguration | весь проект | Отсутствуют security headers (HSTS, CSP, X-Frame-Options и т.д.) | Clickjacking, XSS легче эксплуатируется, MIM | Средняя | Добавить middleware/after_request: установить полный набор headers |
| 11 | A05 Security Misconfiguration | весь проект | Cookie без HttpOnly/SameSite/Secure | XSS-кража сессии, CSRF | Средняя | `app.config['SESSION_COOKIE_HTTPONLY']=True`, `SESSION_COOKIE_SAMESITE='Lax'`, `SESSION_COOKIE_SECURE=True` (production) |
| 12 | A05 Security Misconfiguration | `app.py` `register` | `return f"Ошибка регистрации: {e}", 400` | Утечка имени БД-таблицы и SQL-ошибки клиенту | Низкая | Вернуть нейтральное сообщение |
| 13 | A06 Software Supply Chain Failures | `requirements.txt` | Flask 2.0.1: 2 CVE; Werkzeug 2.0.1: 14 CVE; Jinja2 3.0.1: 5 CVE — итого 20 уязвимостей | RCE через Werkzeug debugger pin (CVE-2024-34069), DoS через Jinja2 (CVE-2024-22195), и др. | Высокая | Обновить: Flask >= 3.1.3, Werkzeug >= 3.1.6, Jinja2 >= 3.1.6 |
| 14 | A07 Authentication Failures / CWE-307 | весь проект | Нет ограничения попыток входа | Brute-force email/password неограниченный | Средняя | Добавить Flask-Limiter с `5 per minute` на /login |
| 15 | A07 Authentication Failures / CWE-521 | `app.py` `register` | Нет проверки сложности пароля | Допускаются пароли `1`, `password`, `qwerty` | Средняя | Минимум 10 символов, ≥3 классов, deny-list |
| 16 | A07 Authentication Failures | `app.py` `login` | Разные сообщения для отсутствующего email и неверного пароля | User enumeration | Средняя | Единое сообщение «Неверный email или пароль» |

## 10. Выводы по работе

1. **Функциональная эквивалентность достигнута.** AI-версия за ~25 минут покрывает все сценарии оригинала: регистрация, логин, подача заявки, решение менеджера, админ-страница, поиск. Это подтверждает тезис, что AI способен быстро выдать рабочий MVP по верхнеуровневому описанию.

2. **Безопасность катастрофически проседает в отсутствие явных запросов на security.** Без подсказок Claude (sonnet-4-5) выбирает удобные для разработки решения (SHA-256, debug=True, role из формы, f-string в SQL), которые в production-сценарии создают **39 уязвимостей по 9 из 10 классов OWASP Top 10**, против **0 эксплуатируемых уязвимостей** в ручной версии после её устранения.

3. **AI хорош в типовых паттернах, но не в защитных.** AI самостоятельно использовал `@login_required`, параметризацию SQL в большинстве запросов, autoescape в Jinja — это «культурные» базовые меры. Но более тонкие практики (объектная авторизация, политика паролей, анти-CSRF, security headers, secret в env, безопасная обработка исключений) не появляются без явного запроса.

4. **AI выбирает устаревшие зависимости «по памяти».** Flask 2.0.1 + Werkzeug 2.0.1 + Jinja2 3.0.1 — комбинация трёхлетней давности с 20 совокупными CVE. AI не сверяется с базой уязвимостей и не предупреждает о них.

5. **AI-версия даже формально не соответствует требованиям ПР6.** Отсутствует журналирование критичных действий, нет хранения секретов вне кода, нет Docker, только 2 сущности БД вместо 3. Минимальный балл за такой код — низкий.

6. **AI-ассистированная разработка в текущем виде требует security-обёртки.** Чтобы получить безопасный код, нужно либо (a) изначально дать AI системный промпт со списком требований OWASP, (b) после генерации провести аудит и доработку (что фактически реализуется в Задании 1, где «AI» был только генератором подсказок), (c) использовать инструменты класса AI-security-reviewer (semgrep с AI-правилами, bandit, pip-audit) поверх AI-кода.

7. **Главный вывод (для отчёта):** AI ускоряет функциональную разработку в **5–10 раз**, но без целенаправленных запросов на безопасность создаёт код **критически слабый по 6+ из 10 классов OWASP Top 10**. AI-ассистированная разработка повышает безопасность только при условии, что разработчик понимает требования безопасности и может их формулировать в виде промптов. Для банковского/медицинского/финтех-сегмента AI-версия в текущем виде **неприемлема для production**.
