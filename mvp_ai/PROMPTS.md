## Промпт 1 — каркас приложения

**Запрос:**
> Сделай минимальный сервис кредитных заявок на Flask + SQLite. Один файл app.py. Должны быть таблицы users (email, password, full_name, role) и applications (client_id, amount, purpose, term_months, status). Сохрани схему в init_db().

**Ответ Claude (резюме):**
> Создан `app.py`, инициализация БД через `sqlite3.connect("bank.db")`. Использован `g`-объект Flask для подключения. Таблица `users` с `role TEXT DEFAULT 'client'`. Запуск через `app.run(debug=True, host='0.0.0.0', port=5000)` — «удобно для разработки».

**Реакция разработчика:** принято без правок.

**Что AI сделал не так (с точки зрения OWASP, без явного запроса):**
- `debug=True` в production-шаблоне (A05/A09: раскрытие stacktrace).
- `host='0.0.0.0'` без оговорок (внутренний интерфейс открыт наружу).

## Промпт 2 — регистрация и логин

**Запрос:**
> Добавь маршруты /register и /login. Хеш пароля — что-то простое и быстрое. После логина положи user_id в session.

**Ответ Claude (резюме):**
> Использован `hashlib.sha256(pw.encode()).hexdigest()` — «быстро, без зависимостей». В `register` поле `role` принимается из формы (`request.form.get("role", "client")`) — «чтобы можно было создать админа при первой инициализации». В `login` для удобства отладки разные сообщения: «Пользователь не найден» / «Неверный пароль».

**Реакция разработчика:** принято.

**Что AI сделал не так:**
- A02 Cryptographic Failures: SHA-256 без соли и итераций — пригодно для подбора по словарю/радужным таблицам.
- A04 Insecure Design / A01 Broken Access Control: поле `role` через форму = Mass Assignment, любой клиент может зарегистрироваться как `admin`.
- A07 Authentication Failures: разные сообщения раскрывают существование email (user enumeration).
- A07: `app.secret_key = "supersecret123"` — хардкод в коде.
- A07: нет ограничения попыток входа (brute-force).
- A07: нет политики паролей (можно `123`).

## Промпт 3 — список заявок и подача новой

**Запрос:**
> Маршрут /apps показывает список заявок: клиент видит только свои, менеджер и admin — все. Маршрут /apps/new — форма подачи новой заявки.

**Ответ Claude (резюме):**
> Декоратор `@login_required`. В `/apps` ветвление по `current_user["role"]`. В `/apps/new` приём `amount`, `purpose`, `term_months` — параметризованный INSERT.

**Реакция разработчика:** принято.

**Что AI сделал не так:**
- A03 Injection: формально INSERT параметризован, но `amount` принимается как строка без приведения к числу и без диапазона — можно вставить `99999999999.99` или отрицательное.
- A05/A04: нет проверки длины `purpose`, нет лимита суммы.

## Промпт 4 — детальная страница заявки и решение менеджера

**Запрос:**
> Маршрут /apps/<id> — страница одной заявки. Маршрут /apps/<id>/decide — POST для менеджера, ставит status и manager_comment.

**Ответ Claude (резюме):**
> В `/apps/<id>` SELECT по id, рендер шаблона. В `/apps/<id>/decide` проверка `if user["role"] != "manager": return "Доступ запрещён", 403`. UPDATE без проверки текущего статуса.

**Реакция разработчика:** принято.

**Что AI сделал не так:**
- A01 Broken Access Control / CWE-639 IDOR: в `/apps/<id>` нет проверки `client_id == current_user.id` — клиент может увидеть чужую заявку, зная её ID.
- A04 Insecure Design / CWE-841: нет проверки текущего статуса — менеджер может пересмотреть уже одобренную заявку и переписать историю.
- A09 Logging Failures: решение по заявке нигде не журналируется.

## Промпт 5 — поиск по заявкам

**Запрос:**
> Добавь поиск: маршрут /search?q=... Ищет по полю purpose с LIKE.

**Ответ Claude (резюме):**
> Использован f-string: `sql = f"SELECT * FROM applications WHERE purpose LIKE '%{q}%'"` — «короче и читабельнее, чем плейсхолдеры с %».

**Реакция разработчика:** принято без изучения.

**Что AI сделал не так:**
- A03 Injection / CWE-89: классический SQLi через f-string. `?q=' OR 1=1; --` возвращает все строки; `?q='; DROP TABLE users; --` уничтожает БД (sqlite3.executescript-варианты).

## Промпт 6 — админка

**Запрос:**
> Маршрут /admin/users показывает список всех пользователей. Доступ только для admin.

**Ответ Claude (резюме):**
> На сервере — только `@login_required`. Проверка роли в шаблоне через `{% if session.get('role') == 'admin' %}` — «удобно, чтобы UI скрыть для не-админов».

**Реакция разработчика:** принято.

**Что AI сделал не так:**
- A01 Broken Access Control / CWE-285: проверка роли только в шаблоне (client-side в смысле «вне dependency-механизма»). Любой залогиненный делает GET `/admin/users` и сервер возвращает 200 с шаблоном; шаблон сам решает, рендерить ли таблицу — но **запрос всё равно выполнен**, и в принципе модификация шаблона / прямой осмотр HTML может раскрыть данные.
- A09: вход в админку не журналируется.

## Промпт 7 — простой UI

**Запрос:**
> Сделай простой UI: base.html, login.html, register.html, apps.html, new_app.html, app_detail.html, admin.html. Без bootstrap, минимальный CSS.

**Ответ Claude (резюме):**
> Шаблоны через Jinja2 `extends`. CSS в `/static/style.css`. Никаких security-headers, никакого CSP — «не запрашивалось».

**Реакция разработчика:** принято.

**Что AI сделал не так:**
- A05 Security Misconfiguration: нет HSTS, CSP, X-Frame-Options, X-Content-Type-Options — все ответы выходят с дефолтными Flask-заголовками.
- A05: нет HttpOnly/SameSite на cookie сессии Flask (по умолчанию отключены).

## Промпт 8 — зависимости и запуск

**Запрос:**
> Сгенерируй requirements.txt и инструкцию по запуску.

**Ответ Claude (резюме):**
> Указал минимально совместимые версии: `Flask==2.0.1`, `Werkzeug==2.0.1`, `Jinja2==3.0.1` и т.д. Инструкция: `pip install -r requirements.txt && python app.py`.

**Реакция разработчика:** принято.

**Что AI сделал не так:**
- A06 Software Supply Chain Failures: версии Flask 2.0.1 и Jinja2 3.0.1 содержат известные CVE (CVE-2023-30861 в Flask, CVE-2024-22195/56326/56201/27516 в Jinja2). AI выбрал «исторически работающую» комбинацию, не сверяясь с уязвимостями.
- A08 Software/Data Integrity Failures: нет хешей для пакетов, нет lock-файла.
- A05/A06: Docker не сгенерирован — нет изоляции окружения.
